## B. 요구서끼리 맞지 않는 곳 (결정 필요)

1. **불가 대안의 "더 긴 기간" 기준**
   - 본문은 "같은 비율일 때 필요한 기간"인데, 예시의 30년은 건물주 몫 **100%** 기준입니다(3억 ÷ 10,099,932 = 29.7 → 30).
   - 상한 95%로 계산하면 31.3 → **32년**이 되어 기간 상한 30년을 넘습니다.
   - 제안: 예시대로 100% 기준, 올림. 30년을 넘으면 `longer` 대안은 빼고 `smaller`만 보여줍니다.
2. **`feasible: false` 판정 기준**
   - `base_ratio`가 95%를 넘을 때만인지, `safe_ratio`가 95%를 넘을 때도 해당하는지 정해 주세요.
   - 예: 기본 90%, 안전 100%인 경우.
   - 제안: `base_ratio` > 95%이면 불가. `safe_ratio`만 넘으면 안전 카드는 95%로 고정하고 `meets_target_low: false`를 보냅니다.
3. **`base_ratio`가 5%보다 낮게 나올 때**: 제안은 5%로 올리는 것입니다.
4. **원 단위 반올림 규칙**: `owner_annual_won`, `tenant_monthly_won`, `max_invest_won`, `payback_years`를 반올림하는지 버리는지 정해 주세요.
   - 예시 값은 두 방식 모두 같게 나와서 구분이 안 됩니다.
   - 프론트는 받은 값을 그대로 표시만 합니다.
5. **숫자 해석을 프론트도 하는지**
   - 규칙 1은 "프론트는 숫자를 다루지 않는다"인데, 3-5는 "서버와 프론트 동일"이라고 합니다.
   - 제안: 해석은 **서버만** 합니다. 프론트는 "내 건물 주소가 뭐였지?" 같은 기기 안 질문만 직접 처리합니다.
6. **기존 화면 수정 범위**: 규칙 8은 "기존 화면을 바꾸지 않는다"인데, 4-2는 다음 두 곳의 수정을 요구합니다.
   - `Picker`에 탭 추가
   - 특약(`draft` 단계)에 공실·승계 조항, 확인 체크 3개, 초안 표시 추가

   이 두 곳은 수정해도 되는 예외로 보면 될까요?

## C. 요구서에 정의되지 않은 형식 (정해 주셔야 프론트를 맞출 수 있음)

1. **비율을 지정한 합의 요청의 응답 형식** (`owner_ratio`가 있을 때)
   - 예: "공사비 팔천만 반반 십오 년"(요구서 예시 그대로).
   - 그 비율을 평가한 결과가 `options`에 어떤 형태로 오나요?
   - 제안: `options`에 `{ "key": "user", "label": "지정한 비율 50%", ... }` 카드 1장(형식은 base/safe 카드와 같음). 카드가 1장이어도 두 줄(기본/낮을 때)로 표시합니다.
2. **이어지는 질문의 맥락 전달**
   - 칩 "안전하게 하면?", "세입자 입장은?"은 직전 조건(공사비·기간)을 알아야 답할 수 있습니다. 서버는 상태를 기억하지 않으니, 프론트가 보내는 형식을 정해 주세요.
   - 제안: `context`에 `last`를 추가합니다.
     ```json
     "context": { "step": "alloc", "bld_id": 1, "viewer": "owner",
                  "invest_won": 50000000, "owner_ratio": 0.7, "target_years": 10,
                  "quarter": "2026Q1",
                  "last": { "intent": "mediate", "invest_won": 50000000, "target_years": 8 } }
     ```
   - 메시지에 공사비나 기간이 없으면 `last`를 먼저 쓰고, 없으면 현재 화면 값(`invest_won`, `target_years`)을 씁니다. 화면 값을 쓰는 게 맞는지, 아니면 `clarify`로 되물어야 하는지 정해 주세요.
3. **`clarify` 칩의 형식**
   - `chips: string[]`만으로는 칩을 눌렀을 때 서버에 무엇을 보낼지 알 수 없습니다(예: "5천만 원인가요?" → [네, 5천만 원]).
   - 제안: `chips: [{ "label": "네, 5천만 원", "message": "공사비 5천만 원, 8년" }]`. 문자열만 오면 label과 message가 같은 것으로 처리합니다.
4. **추천 질문 칩과 `assist_canned`**
   - 단계별 추천 칩 3개는 누가 정하나요? 제안: **프론트가 단계별 고정 목록**을 갖습니다.
   - `assist_canned` 형식 제안: `{ "<칩 문구>": <그 문구로 /api/assist를 부른 실제 응답> }`. 칩 문구는 이 문서 끝의 목록을 쓰겠습니다.
5. **trust의 `data` 형식과 기준 분기**
   - API가 따로 없습니다. `status_code`는 어느 분기의 정산 결과를 쓰나요?
   - 제안: `context.quarter`(화면에서 고른 분기)를 쓰고, 없으면 `demo`의 첫 분기를 씁니다.
   - `data` 형식 제안: `{ "status_code": "...", "metric_checks": {...}, "is_simulated": false }`.
6. **불가 응답과 resolve·analyze 응답에도 공통 필드 넣기**
   - 3장 공통 규칙은 "응답에 항상 `facts`, `notices`, `actions`"인데, 불가 응답 예시와 resolve 응답 예시에는 이 필드가 빠져 있습니다.
   - 빈 배열이라도 항상 넣어 주세요. 불가 응답에도 `annual_saving_won`, `invest_won`, `target_years`를 넣어 주세요.
7. **analyze의 경계 경우**
   - 비교 연도가 2년 전까지 모두 없으면 어떻게 답하나요? 제안: `available: false`와 이유 문장.
   - 데이터 시작(202001) 이전의 달은 어떻게 답하나요? 제안: 위와 같음.
   - "작년"의 기준은 **데이터 마지막 해(2026)**로 고정합니다. 오늘 날짜 기준이 아닌 게 맞나요?
8. **resolve의 `unregistered`와 `residential` 판정**
   - 외부 주소 API를 쓸 수 없으니(외부 요청 0) 판정 방법을 정해 주세요.
   - 제안:
     - 시도·시군구 이름은 알아듣는데 별칭표와 맞지 않으면 `unregistered`
     - "아파트, 빌라, 주택, 오피스텔, 다세대"가 들어가면 `residential`
     - 그 외는 `not_found`
   - bld 2의 `codes`(시군구·법정동·번·지)도 알려 주세요. 프론트는 `S.lookup(codes)` → `/api/building`으로 엽니다.
9. **`set_alloc` 이외의 action 종류**
   - 근거 칩의 `goto`와 [특약 만들기]는 프론트가 직접 처리하겠습니다.
   - 서버가 보낼 수 있는 action 종류를 고정해 주세요. 제안: `set_alloc` 하나와 `goto: { "type": "goto", "step": "base" }`.
10. **LLM 검사 테스트 방법**
    - 완료 기준의 "LLM 응답에 없던 숫자나 금지어를 넣으면 폐기되는지"를 확인할 방법이 필요합니다.
    - 제안 1: 검사 함수를 따로 노출합니다(`check_llm_text(template, text) -> bool`). 단위 테스트가 가능해집니다.
    - 제안 2: 환경변수 `SB_LLM_FAKE="<문장>"`이면 Ollama 대신 그 문장을 LLM 응답으로 씁니다.
